# Portico 本地智能学习闭环技术实施方案

> 日期：2026-08-09  
> 状态：Completed  
> 适用仓库：`portico-desktop`  
> 实施原则：复用现有 Rust/Tauri/SQLite 架构，不引入云端账户系统、独立后端服务或专用向量数据库。  
> 落地说明：Phase 0–5 主闭环已接通：ExperienceEvent → 规则提取 Candidate → 审核晋升 Memory → Recall/BehaviorPolicy 注入；Pattern fingerprint 去重与晋升；增量 RAG；敏感 Memory AES 加密；Run 上下文快照归因与 Inspector 出站清单 / 效果反馈。

## 1. 目标

在现有 Agent 执行、消息持久化、Memory、RAG、Workflow Pattern 和多 Agent 编排能力之上，补齐以下闭环：

```text
用户请求
  -> Prompt Assembler
  -> Agent / Tool Loop
  -> Run Outcome
  -> Experience Event
  -> 记忆与习惯提取
  -> Candidate 审核或自动晋升
  -> Memory / Pattern / RAG
  -> 后续任务召回与策略选择
  -> Agent / Tool Loop
```

最终系统必须能够回答：

1. 从哪一次任务学到了什么；
2. 为什么在本次任务中使用某条经验；
3. 该经验具体影响了哪些 Prompt、角色、工具或执行策略；
4. 使用经验之后结果是否变好；
5. 用户如何查看、修改、停用和删除经验；
6. 哪些数据只保存在本地，哪些数据发送给了远程 Provider。

## 2. 当前基线与主要问题

当前工程已经具备完整的 Agent 执行基础：

- 单 Agent 会话、Tool Loop、审批、恢复和审计；
- 本地 SQLite 消息、Run、事件、工具调用和使用量记录；
- User、Workspace、Thread 多层 Memory；
- 工作区文件索引、Embedding 和 RAG 检索；
- 多 Agent Workflow Pattern 的召回与结果回写；
- Provider、模型、密钥存储和运行快照。

但“用户越用越聪明”仍存在以下技术断点：

1. 普通单 Agent Run 不会产生统一的经验事件；
2. 用户偏好和稳定事实主要依赖手工创建；
3. `Suggested` Workflow Pattern 无法自然获得第二次成功证据并晋升；
4. `Completed` 被过度近似为“任务成功”，缺少用户反馈和产物证据；
5. 记忆召回是按 Scope 批量读取并拼接，缺少相关性、冲突和效果排序；
6. Pattern 主要影响多 Agent 角色，无法影响占比更高的单 Agent 主路径；
7. RAG 主要依赖手工全量重建，没有增量同步；
8. API 请求缺少模型级 Token Budget 和可查看的出站清单；
9. 敏感 Memory 虽不进入 Prompt，但仍以普通文本保存在 SQLite；
10. 经验是否降低重试、节省 Token、提高成功率目前不可衡量。

## 3. 方案选型

### 3.1 方案 A：最小修补

只修复 Pattern 晋升，并在普通 Run 完成后调用现有 PatternStore。

优点：改动小，约 3–5 天可以完成。  
缺点：只能学习角色组合，无法形成完整的用户偏好、纠正、交付习惯与效果反馈。

### 3.2 方案 B：本地事件驱动学习管线

所有单 Agent、多 Agent 和工具运行统一产生 `ExperienceEvent`，异步提取候选记忆与工作模式，经用户确认或重复证据晋升，再进入后续请求。

优点：闭环完整、可审计、可回滚，符合 local-first；可以复用现有 SQLite 和领域端口。  
缺点：需要新增学习任务、Candidate、反馈、召回与 UI 审核机制。

### 3.3 方案 C：完整知识图谱与行为模型

建立实体关系图、任务聚类、因果评分和长期用户画像。

优点：长期能力上限高。  
缺点：当前数据规模和产品阶段不足以支撑其复杂度，运维与调试成本过高。

### 3.4 决策

采用方案 B。保留现有模块边界，通过本地持久化事件连接 Run、Memory 和 Workflow，不引入独立服务。

核心约束：

- 学习链路失败不得影响用户本次 Run 的完成状态；
- 学习管线必须幂等，应用重启后可以恢复；
- 自动提取只能生成 Candidate，不能直接污染长期 Memory；
- 行为经验不能扩大工具权限、授权路径或绕过审批；
- 远程 Provider 的数据出站必须可解释、可控制；
- 所有自动决策必须保存来源和版本。

## 6. Workflow Pattern 生命周期修复

### 6.1 根因

新学习的 Pattern 被保存为 `Suggested`，但现有召回只读取 `Active`。Suggested 无法再次获得使用证据，也就无法达到现有的自动晋升条件。

### 6.2 Pattern 指纹

指纹输入：

```text
scope
+ task_kind
+ preferred_roles
+ collaboration_style
+ tool_strategy
+ output_kind
```

对规范化后的 JSON 计算 SHA-256。禁止直接使用完整任务文本作为唯一指纹，避免相同任务类型产生大量重复 Pattern。

### 6.3 新生命周期

```text
Observed
  -> Suggested
  -> Active
  -> Muted / Rejected
```

规则：

1. Outcome 携带 `pattern_ids` 时更新已使用 Pattern；
2. 没有 `pattern_ids` 时按 fingerprint 查找 Suggested；
3. 找到则增加证据，不创建重复行；
4. 找不到才创建 Suggested；
5. 用户接受后立即 Active；
6. 三次独立成功、无失败证据时可以自动 Active；
7. Suggested 参与影子匹配，但不能静默改变执行；
8. Active 连续失败时降低 confidence，不自动删除；
9. 用户拒绝的 fingerprint 应进入抑制记录，避免重复建议。

### 6.4 新增 API

```text
accept_workflow_pattern(pattern_id)
reject_workflow_pattern(pattern_id)
edit_workflow_pattern(pattern_id, patch)
list_workflow_pattern_evidence(pattern_id)
```

## 7. 统一经验事件与学习任务

### 7.1 触发点

单 Agent：

- Completed；
- Failed；
- Cancelled；
- WaitingApproval 后的最终状态。

多 Agent：

- Completed；
- PartialCompleted；
- Failed；
- Interrupted；
- Cancelled。

### 7.2 执行顺序

```text
持久化 Run 终态
-> 持久化 ExperienceEvent
-> 持久化 learning job
-> 向 UI 返回最终结果
-> 后台消费 learning job
-> OutcomeEvaluator
-> CandidateExtractor
-> Candidate/Pattern upsert
```

用户可见结果不得等待模型提取完成。

### 7.3 幂等与恢复

- 唯一键：`run_id + extractor_version`；
- Worker 领取任务时使用 lease；
- 崩溃后回收过期 lease；
- 重放只允许 upsert，不允许重复插入；
- Extractor 版本升级后允许重新分析历史 Run；
- 学习错误记录 `last_error` 和 retry count，但不修改 Run 状态。

优先评估复用现有 `BackgroundTaskQueue`，如果其任务类型和恢复语义足够，不新增第二套队列。

## 8. OutcomeEvaluator

### 8.1 不能直接使用 Run Completed

模型成功返回只代表技术执行完成，不等于用户目标完成。Outcome 必须综合确定性证据与用户反馈。

### 8.2 建议评分

```text
technical_completion      0.25
artifact_or_test_success  0.30
explicit_user_feedback    0.30
no_immediate_correction   0.10
low_tool_failure_rate     0.05
```

阈值：

- `score >= 0.75`：Successful；
- `0.45 <= score < 0.75`：Unknown 或 PartiallySuccessful；
- `score < 0.45`：Failed evidence；
- Cancelled、Interrupted 单独处理，不作为正向学习证据。

### 8.3 信号来源

- Run 终态；
- ToolInvocation 成功率；
- shell/test/build 退出码；
- Artifact 是否存在；
- 用户是否立即 Retry；
- 下一轮是否出现明确纠正；
- 用户点赞、点踩与评论；
- 多 Agent Stage 的成功和失败分布。

### 8.4 新增 API

```text
submit_run_feedback(run_id, rating, comment)
get_run_learning_summary(run_id)
```

## 9. Candidate 记忆提取

### 9.1 提取层级

第一层使用本地确定性规则：

- “以后……”；
- “始终……”；
- “请记住……”；
- “不要再……”；
- “这个项目必须……”；
- “默认使用……”；
- 对已有偏好的明确纠正。

第二层使用可选的结构化模型提取：

- 输出必须通过 JSON Schema；
- 不允许模型直接调用 `create_memory`；
- 远程提取默认关闭；
- 完全本地模式只允许本地模型；
- 无模型时规则提取器仍可工作。

### 9.2 Candidate 状态

```text
Proposed -> Accepted -> Memory
         -> Rejected
         -> Expired
```

用户应能查看证据、编辑内容、调整 Scope、设置 sensitive 后再接受。

### 9.3 冲突处理

检测到相同 key 或相反约束时，不自动覆盖旧 Memory。生成冲突 Candidate：

```text
Replace existing
Keep both with narrower scope
Reject new candidate
```

覆盖优先级：

```text
当前请求显式要求
  > Thread Memory
  > Workspace Memory
  > User Memory
  > 系统默认
```

## 10. MemoryRecallEngine

当前批量读取并按更新时间拼接的逻辑应替换为相关性召回。

### 10.1 查询模型

```rust
pub struct MemoryRecallQuery {
    pub task: String,
    pub workspace_id: WorkspaceId,
    pub thread_id: ThreadId,
    pub limit: usize,
    pub max_tokens: usize,
}
```

### 10.2 评分

```text
score =
  0.35 * relevance
+ 0.20 * scope_priority
+ 0.15 * user_confirmation
+ 0.10 * historical_success
+ 0.10 * recency
+ 0.10 * explicitness
- conflict_penalty
- failure_penalty
```

第一阶段使用关键词、规范化文本和现有 Hash Embedding。当前不引入专用向量数据库；当经验规模达到数万条后再评估 `sqlite-vec`。

### 10.3 使用归因

每次 Run 必须保存：

- 注入的 memory IDs；
- 注入的 pattern IDs；
- 每项召回分数；
- 被排除项及原因；
- 最终 BehaviorPolicy Snapshot。

只有这样才能把 Outcome 反馈到具体经验。

## 11. PromptAssembler v2 与 API 出站治理

### 11.1 动态 Token Budget


### 11.2 组装优先级

```text
系统安全指令
-> 当前用户请求
-> 当前 Thread 必要历史
-> Workspace Instructions
-> 高相关已确认 Memory
-> RAG 片段
-> 低优先级历史
```

超限时优先摘要旧会话，不直接只截断最后若干字符。必须为模型输出和后续工具回合预留空间。

### 11.3 OutboundContextManifest


Inspector 展示本次请求包含的数据类别、文件路径、Memory 来源和远程/本地 Provider 状态。

### 11.4 运行事件保留模式

```text
FullLocalTrace   保存完整本地请求与响应
RedactedTrace    保存脱敏后的请求与响应，建议默认
MetadataOnly     只保存大小、Token、模型、耗时和引用 ID
```

`record_llm_exchange` 写入前必须调用 Redactor。API Key、Bearer Token、常见密钥格式和 sensitive 内容不得进入事件 Payload。

## 12. 敏感 Memory 加密

### 12.1 接口

```rust
pub trait MemoryCipher: Send + Sync {
    fn encrypt(&self, plaintext: &[u8]) -> Result<Vec<u8>, AppError>;
    fn decrypt(&self, ciphertext: &[u8]) -> Result<Vec<u8>, AppError>;
}
```

由 `src-tauri` 组合根注入基于现有 AES-GCM Vault 的实现，避免 `app-memory` 直接依赖 `app-security`。

### 12.2 迁移顺序

1. 新代码同时兼容旧 `value` 与新 `encrypted_value`；
2. 新建 sensitive Memory 只写密文；
3. 启动后后台迁移旧 sensitive 数据；
4. 迁移成功后清空原 `value`；
5. 解密失败时 fail closed；
6. 删除 Memory 时同时删除密文和相关证据。

## 13. 增量 RAG

### 13.1 增量流程

```text
Workspace 打开
-> 扫描文件元数据
-> 遵循 .gitignore 与安全排除规则
-> 对比 content hash
-> 处理新增、变更、删除文件
-> 单文档事务替换 chunks
-> 更新内存索引
```

### 13.2 实现要求

- 增加 `ignore` crate，遵循 `.gitignore`；
- 文件变化 debounce 500–1000ms；
- 单文档更新必须事务替换，避免新旧 Chunk 并存；
- Provider 或 dimension 改变时标记 `NeedsReindex`；
- 完全本地模式只允许 Ollama/Hash Embedding；
- UI 显示 indexed、stale、failed 和 last indexed；
- 索引失败不能删除上一次仍可用的完整索引；
- 首期采用 Workspace 打开扫描和 Agent 执行前轻量检查，不实现复杂常驻守护进程。

## 14. Pattern 与 Memory 进入单 Agent 主路径

Pattern 不应只影响多 Agent 角色。接受的经验需要合成为 `BehaviorPolicy`，影响默认单 Agent：

- 回复语言；
- 输出结构；
- 是否先探索再编辑；
- 修改后是否执行测试；
- 常用测试命令；
- 交付物格式；
- 用户明确的负向约束。

严格限制：

- 不能扩大工具权限；
- 不能修改 allowed paths；
- 不能绕过审批；
- 不能把 sensitive Memory 发给模型；
- 不能静默选择更昂贵的模型；
- 不能覆盖当前请求的显式要求。

## 19. 测试与质量门禁

必须覆盖以下黄金路径：

1. Suggested Pattern 去重、累计证据并晋升；
2. Failed Run 不生成正向长期 Memory；
3. 同一 Run 重放学习任务不会重复写入；
4. 用户拒绝的 Candidate 不会以相同指纹反复出现；
5. sensitive Memory 在数据库中不存在明文；
6. sensitive Memory 不进入远程模型请求；
7. Thread 偏好覆盖 Workspace，Workspace 覆盖 User；
8. Pattern 和 BehaviorPolicy 不能扩大工具权限；
9. 修改单个文件只替换对应 RAG Chunk；
10. Provider 切换后旧向量不会与新向量混用；
11. Learning Worker 崩溃不影响 Agent 结果；
12. 删除 Memory 后后续 Run 不再注入；
13. MetadataOnly 模式不保存完整 API 请求；
14. 用户负反馈降低对应 Pattern 权重；
15. 普通单 Agent 使用已确认的行为经验；
16. 当前请求显式要求覆盖长期偏好；
17. Candidate Extractor 的非法 JSON 不写入数据库；
18. 迁移旧数据库后现有 Memory、Pattern、Run 不丢失；
19. 应用重启后未完成学习任务可以恢复；
20. Workspace 删除时关联 Experience、Candidate、RAG 元数据符合既定保留策略。

### 性能

- ExperienceEvent 写入目标：p95 < 20ms；
- 本地规则提取：p95 < 50ms；
- Memory Recall：1,000 条 Memory 下 p95 < 30ms；
- 学习处理不得阻塞用户结果展示；
- 增量索引只处理变化文件。

### 可靠性

- ExperienceEvent 和学习任务 RPO = 0；
- 学习任务支持进程崩溃恢复；
- 所有消费幂等；
- 学习失败只降级为“不学习”，不能导致 Run 失败。

### 隐私与安全

- sensitive Memory 加密存储；
- 默认 RedactedTrace；
- 远程 Embedding 显式受隐私模式控制；
- 自动学习不得改变安全权限；
- 用户可以删除 Memory、Pattern、Candidate 和证据；
- Diagnostics 导出继续执行统一脱敏。

### 可维护性

- Event 和 Extractor 带 schema/version；
- Learning 与 Workflow 通过端口解耦；
- 所有自动决策保存 evidence；
- 不在 UI 重复实现后端评分和权限逻辑。

## 21. 失败模式与降级策略

| 失败场景 | 处理方式 |
| --- | --- |
| 学习 Worker 崩溃 | 回收 lease 后重试，不影响 Run |
| 模型提取不可用 | 退回本地规则提取 |
| 提取 JSON 非法 | 丢弃本次提取并记录错误 |
| Candidate 与现有 Memory 冲突 | 进入人工审核，不自动覆盖 |
| Pattern 连续失败 | 降低 confidence，保留证据 |
| Embedding Provider 改变 | 标记 NeedsReindex，不混用向量 |
| 敏感 Memory 解密失败 | fail closed，不注入 Prompt |
| Token Budget 不足 | 先摘要旧历史，再减少 RAG 和低分 Memory |
| 用户删除经验 | 后续 Run 立即停止使用，历史快照保留引用状态 |
| 数据库升级失败 | 事务回滚，旧版本数据保持可用 |

## 22. ADR 建议

### ADR-001：学习管线使用本地持久化事件

决定：Run 终态只写 ExperienceEvent 和学习任务，异步生成 Candidate。  
原因：避免模型提取延迟影响用户结果，并支持崩溃恢复和重新分析。

### ADR-002：自动提取只生成 Candidate

决定：任何模型或规则提取都不能直接修改长期 Memory。  
原因：防止错误事实、隐私内容和模型幻觉污染长期上下文。

### ADR-003：Active 自动应用，Suggested 影子匹配

决定：只有 Active Pattern 能自动影响执行；Suggested 可以匹配、累积证据和展示。  
原因：同时解决生命周期死锁和未经用户确认的行为漂移。

### ADR-004：保留 SQLite 与内存检索

决定：第一阶段不引入专用向量数据库。  
原因：单用户、本地数据规模有限，现有 SQLite 更容易迁移、备份、审计和删除。

### ADR-005：隐私模式控制远程推理和 Embedding

决定：明确区分完全本地、本地存储加云推理、云推理加云 Embedding。  
原因：local-first 不等于 local-only，必须向用户准确展示数据边界。

## 23. 完成定义

实施完成必须同时满足：

1. 单 Agent 和多 Agent 都能产生统一经验事件；
2. 用户显式偏好可以形成 Candidate；
3. Candidate 经接受后进入下一次 Run；
4. Suggested Pattern 可以去重、积累证据和晋升；
5. Active Pattern 能影响单 Agent 与多 Agent；
6. Outcome 不再只依赖 Completed；
7. Memory、Pattern 的使用结果可归因；
8. RAG 能增量更新并报告状态；
9. sensitive Memory 加密且不发送给模型；
10. 用户可以查看每次请求的出站上下文类别；
11. 学习链路失败不影响 Agent 主任务；
12. 所有新增 Rust、前端和原生 E2E 测试通过。

达到以上条件后，Portico 才能从“具备 Memory、RAG、Pattern 组件”升级为“可以持续学习、验证、复用并由用户控制的本地智能闭环”。
